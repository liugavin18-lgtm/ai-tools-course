# 第 6 章　实战案例：管理多个本地数据库

!!! abstract "本章目标"
    通过一个真实项目的完整过程，学会：① 如何从需求走到设计；② 一个“注册表”式的多数据库服务怎么做；③ 真实开发中会踩哪些坑，怎么发现和修复。

## 6.1　背景和需求

某个团队有十几个本地 SQLite 数据库，由多个定时任务每天写入。他们经常要：

- 问一句：“今天各个库更新了吗？”
- 临时查几条数据做核对。
- 确认定时任务有没有悄悄挂掉。

**旧办法：** 打开终端，找库路径，写 SQL，查日志。每次都要折腾，而且容易误改数据。

**目标：** 用一句大白话，就能完成查询和检查，**并且保证绝对不会改坏数据**。

## 6.2　需求拆成设计

| 需求 | 设计决定 |
|---|---|
| 要管理很多库 | 做一份**注册表**（`registry.json`），登记库名、路径、说明 |
| 不会改坏数据 | **只读**，三层防线（第 5 章） |
| 问“更新了吗” | `list_databases` 返回大小、**最后修改时间** |
| 问“任务挂了吗” | `tasks` 读取系统定时任务的状态和**上次退出码** |
| 想看有什么表 | `describe` |
| 想查数据 | `query`，限制行数和超时 |

**共 4 个工具**，在“5~10 个”的健康范围内。

### 注册表的作用

```json
{
  "databases": {
    "orders":   {"path": "~/data/orders.db",   "desc": "订单库",   "writers": ["job.orders.daily"]},
    "customers":{"path": "~/data/customers.db","desc": "客户库",   "writers": []}
  }
}
```

!!! tip "为什么用注册表，而不是让 AI 传路径"
    如果工具允许 AI 传任意文件路径，它就能读到磁盘上任何数据库。**用注册表，只有登记过的库才能被访问**，这是“最小权限”的体现。AI 只能传**库名**，路径由服务端查表得到。

    同样，备份目录里可能有上百个副本，**不要登记**，否则会淹没有用的信息。

## 6.3　核心做法：用名字找路径，再只读打开

```python
def _path(name: str) -> Path:
    if name not in REG:
        raise ValueError(f"未登记的库 {name!r}，可选：{', '.join(REG)}")   # 错误信息直接列出可选项
    p = Path(REG[name]["path"]).expanduser()
    if not p.exists() or p.stat().st_size == 0:
        raise ValueError(f"{name} 文件不存在或为 0 字节")
    return p
```

## 6.4　开发中真实踩到的三个坑

### 坑 1：SDK 升级后服务直接起不来
**现象：** 客户端报 `Connection closed`，没有任何有用信息。
**排查：** 不通过 AI，直接在终端手动运行服务，才看到真实报错：`No module named 'mcp.server.fastmcp'`。
**原因：** SDK 2.x 把 `FastMCP` 改了名。
**修复：** 依赖固定为 `mcp>=1.2,<2`。
**教训：** ① 依赖要固定上限；② **“Connection closed”几乎都是服务启动失败，先手动跑一遍**。

### 坑 2：只读防线把合法操作也挡了
**现象：** 查询表结构的工具对任意表都失败，报 `not authorized`。
**原因：** “只放行读操作”的授权回调，把 `PRAGMA table_info`（查字段，本身只读）也一并拒绝了。
**怎么发现的：** 写示例的**自动化测试**时，`describe_table` 那一条红了。而之前手动试的是“不带表名”那一分支，恰好没触发。
**修复：** 单独放行 `table_info` 这一个 PRAGMA，其余 PRAGMA 仍然拒绝，并立刻回归测试“写入仍被拒”。
**教训：** ① **每个工具、每个分支都要测**；② 修复安全相关代码后，**必须重新跑一遍“应该被拒绝”的测试**。

### 坑 3：工具注册了，AI 却说“没有这个工具”
**现象：** 配置正确、连接正常，但某个 AI 工具回答“当前会话中没有该工具”，转头去用终端命令自己翻文件。
**原因：** 该工具采用“按需加载”机制，需要在配置里标记为延迟加载，让它走“先公告、再加载”的流程。
**修复：** 配置中加 `"deferred": true`，并在提问里明确要求“用 xxx 这个 MCP”。
**教训：** **不同 AI 应用对 MCP 的呈现方式不同**，换一个客户端就要重新验收一次。

## 6.5　验收：用“假装是 AI”的脚本

```python
# 正常使用应该成功
await call("list_databases", {})
await call("describe", {"db": "orders", "table": "orders"})

# 越权必须失败
await call("query", {"db": "orders", "sql": "create table x(a)"})          # 写：必须拒绝
await call("query", {"db": "orders", "sql": "pragma journal_mode=delete"}) # 改设置：必须拒绝
```

## 6.6　用起来是什么样

| 你说 | AI 做什么 |
|---|---|
| “今天各个数据库更新了吗？” | 调 `list_databases`，对照最后修改时间 |
| “有哪些任务失败了？” | 调 `tasks`，找上次退出码不为 0 的 |
| “订单表最近 7 天有多少单？” | `describe` 看字段 → `query` 统计 |

**意外收获：** 第一次运行就发现某个库已经一个月没更新。如果只看文件夹，这种“悄悄停更”很难发现。**这就是只读监控型 MCP 的价值。**

## 6.7　这个案例的设计清单

- [x] 注册表限定可访问范围
- [x] 只读三层防线，默认拒绝
- [x] 返回有上限、有超时
- [x] 4 个工具，职责清晰
- [x] 自动化测试覆盖“必须拒绝”
- [x] 依赖版本固定
- [x] 写入类能力**没有做**，需要时另建带审批的独立服务

## 本章练习

**练习 6.1**　把你自己的两个 SQLite 文件做成注册表，仿照本案例写一个 `list_databases`，返回名称、大小、最后修改时间。

**练习 6.2**　再增加一个 `freshness_report()`：把“最后修改时间超过 3 天”的库标成“可能停更”。思考：哪些库本来就不需要每天更新？怎么在注册表里表达这个差异？

??? success "参考思路"
    在注册表里为每个库增加 `max_age_days` 字段（如日更库为 2，静态库为空表示不检查），`freshness_report` 只对设置了该字段的库做判断。
